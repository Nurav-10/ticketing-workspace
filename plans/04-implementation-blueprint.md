# Phase 4 implementation blueprint — Workflows, views and search

**Status:** planned; blocked on Phase 3 exit evidence. **Updated:** 14 November 2026. This blueprint expands [Phase 4](04-workflows-views.md). It is a delivery plan, not evidence that Phase 3 or Phase 4 is complete.

## Readiness gate and repository starting point

Phase 4 depends on the Phase 3 issue vertical slice and the Phase 1/2 identity, authorization and accessible shell foundations. The current Phase 3 blueprint explicitly says implementation is in progress and exit evidence is pending. It also records incomplete Phase 1/2 dependencies. Do not activate Phase 4 configuration or view controls until the owners have recorded the required Phase 1/2 and Phase 3 evidence, including protected issue reads/writes, stable version semantics, real persisted UI state, and private-team isolation.

There is useful but incomplete groundwork: `issue-domain.ts` has the built-in status set (`backlog`, `todo`, `in_progress`, `done`, `canceled`), a fixed transition graph, and list filters for status, priority, assignee and archive state. The Prisma schema currently stores `Issue.status` as a PostgreSQL enum. Existing list paging uses a `(createdAt, id)` keyset. These are Phase 3 defaults, not configurable workflow or Phase 4 acceptance. Phase 4 must preserve the issue service/repository boundary and replace the hard-coded workflow through an injected workflow contract rather than adding more status conditionals to routes or React.

Before coding, record decisions for: status categories and terminal behavior; default transition policy; who can administer workflows; saved-view visibility/edit rights; whether board order is shared or personal; label scope; search language/tokenization; supported sort choices; and how view state is encoded in URLs. Recommended initial defaults are workspace owners/admins managing team workflows, private-by-default personal views plus explicit team-shared views, shared team board order, workspace/team labels only, and title/description PostgreSQL search. Do not expose a workspace-wide view over private-team results unless each request still applies the viewer's team policy.

## Module ownership and seams

Keep the existing direction: `web feature → typed API client → protected routes → application service/domain → repository port → Prisma/PostgreSQL`. Add a workflow application/domain module and persistence adapter; issue commands receive a workflow port (or resolve status policy from the repository transaction) instead of importing fixed enum rules. Routes validate and serialize. The repository is responsible for tenant predicates, transaction/locking, stable page semantics and policy facts. The browser never authorizes itself based on cached view membership.

Suggested ownership (adapt to current naming):

| Area | Owns |
| --- | --- |
| `apps/api/src/workflows/` | Status/category/transition types, configuration commands, default workflow policy and validation |
| `apps/api/src/issues/` | Issue query/filter contract, workflow-aware transition command, labels/search semantics |
| `apps/api/src/views/` | Saved view schema, scope/permissions, CRUD and safe filter serialization |
| Prisma adapters | Scoped SQL/Prisma queries, keyset cursors, FTS, rank allocation, migration-era compatibility |
| `apps/web/src/features/issues/` | Shared filter model, list/board presentation, issue navigation and search states |
| `apps/web/src/features/workflows/` and `views/` | Admin editor, saved-view picker/CRUD, validation and accessibility |

Add shared wire contracts only for stable browser/API shapes. Avoid sharing generated Prisma types or storing arbitrary client query objects.

## Data and migration sequence

All schema changes are additive first and use a new migration after applied history. Preserve the current schema baseline and existing issues. Produce an explicit backup/forward-recovery note before introducing a data rewrite; application rollback must not drop status, label, view or search data.

1. **Workflow tables:** add `workflow_statuses` with UUID, workspace/team IDs, stable key, display name, category (`backlog`, `unstarted`, `started`, `completed`, `canceled`), position, default flag, active/retired state and configuration version. Enforce unique team/key and team/position as appropriate, checks for valid category/position/default counts, and composite FKs back to the same workspace/team. Add `workflow_transitions` with scoped source/target status IDs and unique edges. Status IDs stay stable across rename/reorder; names and keys are not authorization credentials.
2. **Issue status expansion:** add nullable `workflow_status_id`, seed one team workflow matching each legacy enum value, and map existing issue statuses to the seeded status IDs. During an expand/contract window, deploy code that can read the new ID with a legacy fallback and writes both representations in the same transaction. Backfill in bounded batches, verify every issue maps to exactly one status, add the non-null composite FK/check/index, then deploy code that reads/writes only the new relation. Drop the legacy enum column/type only in a later reviewed contract migration after no supported binary reads it. If deployment is strictly single-version, still preserve this ordering in separate migrations/releases; do not combine an irreversible conversion and feature activation.
3. **Workflow administration concurrency:** use a team workflow/config version and optimistic `expectedVersion` for rename, reorder, default and transition-edge changes. Lock in the documented order (workspace → team → memberships → workflow rows → issue/order rows). A transition request resolves source, target and edge inside the same authorized transaction, checks issue `expectedVersion`, updates status/version and writes issue activity/outbox atomically. Configuration edits cannot leave a default missing or point an edge to a retired status.
4. **Deletion/reassignment:** treat statuses with issues as retire/reassign operations. Require an explicit active target in the same team; in one transaction validate permission and expected workflow/issue state, move affected issues, update versions and product activity/outbox records, remove/replace transitions and retire the old status. If atomic bulk reassignment exceeds a documented transaction bound, use a staged job with a visible in-progress state and prevent final retirement until every issue is moved; never strand issues or silently cascade-delete them.
5. **Labels and board order:** add scoped labels and issue-label joins with composite workspace/team/issue FKs. Define whether a label is workspace-wide or team-only before schema finalization; a team-only label cannot be applied cross-team. Add board order storage with a team/status scope and deterministic tie-breaker. Keep order data separate from descriptive issue fields if rebalancing should not create false content edits.
6. **Saved views:** add `saved_views` with UUID, workspace/team scope, creator, name, visibility (`private` or `team` initially), validated versioned filter/group/sort JSON, layout, configuration version and timestamps. Add same-tenant FKs and indexes for team-shared and owner-private lookups. Do not store arbitrary SQL, raw URLs, descriptions or opaque unvalidated query fragments. A personal view is readable/editable only by its owner; a team view is visible to authorized team readers and editable by its owner or an authorized team admin under the recorded policy. Deleting a member should transfer, privatize or remove owned shared views by an explicit, audited rule.
7. **Search support:** add a maintained PostgreSQL `tsvector` (generated column or transactionally maintained expression chosen after migration compatibility review) over title and description, plus a GIN index. Choose and document the text-search configuration and query syntax; do not leak descriptions into logs, URLs, snippets or telemetry. Keep search data derived from current issue text so title/description edits and migration backfill cannot drift.

## API contracts and query semantics

Continue `/api/v1` and existing success/error envelopes. Reject unknown fields, duplicate singleton query parameters, invalid IDs and out-of-range values. Use `404` for resources outside requested tenant/team scope to avoid existence leaks, `403` only for an in-scope action with a policy-specific denial, `409` for stale config/issue/order versions or invalid transitions, and bounded generic errors for storage failures.

Proposed endpoints (names may follow the existing router conventions):

- `GET/POST /workspaces/:workspaceId/teams/:teamId/workflow/statuses`; `PATCH` a status; explicit transition-edge create/delete; and a retire/reassign command. Writes require team-admin policy and expected workflow version.
- `GET /.../workflow` returns one authorized canonical configuration and version for UI initialization.
- `GET /.../issues` accepts bounded filters: status ID(s), category, priority, assignee, label IDs with documented ANY/ALL semantics, archive mode, search term, sort key/direction, group mode, limit and cursor. Project filter is deferred to Phase 6. Preserve a documented default sort and stable ID tie-breaker; document null placement for assignee/other nullable keys.
- `GET /.../issues/search` may be a separate endpoint if it simplifies relevance/snippet shape; it must share the same authorization and filter compiler as list results.
- `POST /.../issues/:issueId/transitions` resolves target status by ID and checks the current workflow edge and issue version in the mutation transaction. Legacy Phase 3 status strings may be accepted only during a short compatibility window and must resolve to an in-team status.
- `GET/POST /.../views`, `GET/PATCH/DELETE /.../views/:viewId` validate a fixed, versioned filter grammar. CRUD always resolves the view under workspace/team and enforces its visibility/edit policy. Shared view URLs identify the view, not serialized protected issue content.
- `POST /.../issues/:issueId/board-position` moves an issue to a target status/group and optional before/after anchor, requiring expected issue version plus a board/order version. The server resolves anchors under the same team and active filter scope.

Cursor paging must be keyset-based and deterministic for every supported sort, with explicit `NULLS FIRST/LAST` semantics and ID as the final tie-breaker. Cursors are opaque, bounded and bound to workspace, team, normalized filter hash, sort/group and ordering version; reject a cursor replayed with different filters or scope. Do not use offset paging for growing boards/lists. Define whether a page is a snapshot or a live traversal; on data/order changes, return a recoverable stale-cursor response and let the client refresh rather than silently skip/duplicate issues. Cap page size and query complexity; cap label/status lists and search input length.

PostgreSQL full-text search initially searches authorized titles and descriptions. Apply workspace membership, team visibility/private-team membership, archive policy and every filter in the database query before ranking, snippets, totals or facets are produced. Use deterministic relevance ordering with a stable ID tie-breaker. A query returning zero authorized rows must not reveal whether inaccessible matching issues exist through counts, timing-shaped error differences, snippets or facets. Validate search syntax and fall back to a documented safe plain-text query form; do not expose raw tsquery errors.

## Authorization, saved-view privacy and concurrency

- Every workflow, issue, label, view, count and search operation requires a verified principal and exact authorized workspace/team. Repository queries include workspace and team predicates; do not fetch a global UUID/key then authorize afterward. A workspace owner/admin does not bypass private-team membership unless the established Phase 1 policy explicitly changes and is reviewed.
- Workflow read follows team read policy; mutation uses explicit team-admin capability. The server rechecks active workspace membership, private-team membership and role facts in the transaction to prevent revocation races. Workflow status IDs from another team, workspace or retired workflow resolve as invalid/not-found without disclosing their existence.
- Issue transition, status retirement/reassignment and board moves use expected versions. For board order, serialize moves only within a team/status group (or a narrower group lock) and allocate sparse integer ranks with a documented rebalance procedure; use stable issue ID as collision tie-breaker. Return the canonical rank/order version. Concurrent stale moves get a conflict and a refresh/reapply path. Rebalance must be bounded and transaction-safe; if needed, stage it and mark the group as reordering rather than partially changing visible order.
- Every issue-changing operation writes issue state, activity and outbox in the same transaction. Workflow config audit/activity is distinct from ordinary security audit; record actor, scoped resource and safe before/after identifiers without user text. Failed/stale commands write no partial records.
- Saved view definitions can contain status, assignee and label identifiers, but these are not grants. On every read/execute, validate the view's scope and current authorization, then compile its filters through the same query path as an ad hoc list. Removed/retired filter references are normalized or surfaced as an editable stale-view warning; never broaden a query silently. Never include view filters or names that reveal inaccessible private-team metadata in shared URLs.
- Configure strict upper bounds for filter counts, status transitions, page size, search text, result snippets and transaction duration. Retry only known deadlock/serialization errors with bounded attempts and safe commands.

## Web delivery slices and accessibility

Build on the Phase 2 shell and Phase 3 issue API boundary. Keep URL state (authorized filters, layout, grouping and sort) canonical and restorable through back/forward. Do not place issue titles/descriptions or private data in query strings. Opening detail preserves the list/view state and returns to the same authorized result context.

1. **Workflow read contract and migration seam:** expose canonical workflow configuration; show statuses in existing issue controls using server-provided IDs/names/categories. Preserve an explicit compatibility fallback only until the staged migration retires legacy fields. No admin editor yet.
2. **Workflow administration:** add accessible status create/rename/reorder, category/default and transition-edge editor. Use a dialog or focused panel with labeled fields, inline validation, keyboard-operable reorder controls, visible save/version state and conflict reload/reapply. Status retirement presents affected issue count and explicit reassignment target before commit; screen readers hear progress/result.
3. **Shared list query model:** one validated client-side filter state powers list, board and URL encoding. Add filters incrementally (status, priority, assignee, labels, archive/search); selected filter chips, reset, loading/error/empty states and result counts are clear. Counts are server-authorized and never inferred from hidden rows.
4. **Board and ordering:** render status columns from workflow configuration and reuse the same filters as list. Pointer drag is optional enhancement; provide a keyboard menu or buttons for moving status and ordering before/after a named issue, with visible focus and live announcement. On concurrent move conflict retain intent and offer refresh/reapply. Touch targets remain usable on narrow screens.
5. **Search:** provide labeled search input, debounce only client requests (server limits remain authoritative), abort stale requests, announce result count once, highlight safely escaped text and preserve empty/no-match/error distinctions. Do not render raw HTML snippets.
6. **Saved views:** create, rename, update and delete views under explicit Personal/Team sections. Confirm team-shared visibility, show owner/edit rights, and explain stale references. Private views are not rendered for another actor even if a URL is copied. Provide unsaved view state handling and clear save feedback.

All controls use semantic buttons, links, inputs and list/grid semantics; keyboard focus remains visible; no action depends on color, hover, drag or animation. Dialogs manage focus, Escape and restoration. Support screen-reader labels/announcements, reduced motion, contrast, 200% zoom, and the existing 360/768/1024/1440 viewport checkpoints. Keep motion restrained and avoid animating every row or column reflow. Browser back/forward, refresh, loading, empty, denied, offline, stale cursor, conflict and save error states must be designed and exercised.

## Incremental implementation and review checkpoints

Each slice should be independently reviewable and remain behind the previous acceptance gate. Do not mark Phase 4 complete just because a model or endpoint exists.

1. **Readiness/decision record:** obtain Phase 1/2 and Phase 3 evidence and decisions above. Review current `plans/03-implementation-blueprint.md` handoff and preserve its contracts. If any gate is missing, stop Phase 4 feature activation and report it; schema discovery/planning can continue without claiming readiness.
2. **Workflow domain and compatibility migration:** introduce workflow types/port and additive seeded workflow rows for current enum values. Implement expand/backfill/verify/contract migrations and rollback-forward notes. Existing issue create/list/detail/edit/transition continue to work across deployment stages.
3. **Workflow admin API and transaction rules:** add configuration CRUD and safe retire/reassign with role/private-team matrix, expected configuration version, constraints, activity and outbox semantics. Add Docker PostgreSQL cases for concurrent admin writes and stale configs.
4. **Workflow UI + issue transition integration:** status controls consume canonical workflow; team admin editor supports all decisions; members can transition only along configured edges. Exercise keyboard and conflict recovery before proceeding.
5. **Labels and normalized filter compiler:** implement label scope/join and one bounded query compiler shared by list, board, views and search. Add property/integration coverage for combinations and authorization isolation.
6. **Stable list paging + board order:** add supported sort/group modes, filter-bound cursors, sparse-rank ordering and concurrency handling; make the list and board use the same result semantics. Record query plans/index evidence at representative data volume before adding indexes beyond those justified by measurements.
7. **Search:** add title/description FTS index/backfill/maintenance and bounded API shape; prove search result, snippet and count isolation for private teams.
8. **Saved views:** implement versioned grammar, scope/edit checks, CRUD, URL navigation and stale-reference behavior. Add copied-URL and changed-membership cases.
9. **Integrated review/handoff:** security review of every query path and mutation lock order; migration readiness/recovery note; API/UI acceptance evidence; outstanding decisions, operational risks and follow-up performance work. Phase 4 status remains pending until its exit evidence is attached.

## Docker-only validation plan

Follow the repository rule in the Phase 3 blueprint: do not install packages or run Bun/Node/Prisma checks on the host. Use the existing Compose-built images and isolated disposable `db-test`; never run migration experiments, reset scripts or cleanup against the development `db` volume or production. Do not relax the test database allowlist. Generate/validate Prisma artifacts in Docker only. If a dependency manifest or lockfile changes, run the dependency safety review required by repository policy.

After implementation, record exact Docker commands, image/database identity and results for:

- API/web typecheck and production builds; Prisma schema/client generation and all additive migrations from an empty test DB and a safe copy representing the existing Phase 3 schema/data.
- Migration upgrade cases: all five legacy statuses map to one per-team status; zero issues are lost or left unmapped; repeated/partial backfill is safe; constraints block cross-team status links; old/new application compatibility is as documented; rollback keeps new data and uses forward recovery rather than dropping tables.
- Workflow domain/API: category/default invariants, transition graph, invalid/retired/cross-team statuses, unauthorized admins/members, stale config versions, in-use status reassignment atomicity, concurrent rename/reorder/edge edits, no activity/outbox on failure and one transaction for successful issue moves.
- Tenant/privacy: workspace A/B and public/private team matrix across list, board, search, snippets, counts, labels and saved views; workspace admin outside private team denied; copied private-view URL denied; guessed UUID and status/view IDs do not disclose existence.
- Query behavior: strict filter grammar and size limits, keyset pagination for each supported sort with null ordering/tie IDs, filter-bound cursor replay rejection, concurrent insert/move behavior, label ANY/ALL behavior, archived defaults, FTS updates after title/description change, and no raw search syntax or SQL leakage.
- Saved views and concurrency: private owner vs other member; team-shared read/edit policy; stale versions; deleted owner rule; removed-status/label references; two simultaneous board moves to same gap, stale move conflict, deterministic reordering and safe rebalance.
- Web typecheck/build and browser-based keyboard, screen-reader announcement, reduced-motion, focus, back/forward, copied URL, 200% zoom, and 360/768/1024/1440 layouts. Record observable evidence; a plan or unit test alone is not accessibility acceptance.
- Query plans and representative latency for list/filter/search, including realistic large-team cardinality. Add/adjust indexes only in response to measured query plans and record the target load before making performance claims.

## Phase 4 exit evidence

Exit only when authorized team admins configure a workflow; ordinary members see that canonical configuration and can make only allowed, version-checked transitions; status retirement never strands issues; list, board, filters, search, counts and snippets remain tenant/private-team safe; saved views obey their declared scope/edit policy; ordering and pagination are deterministic under concurrent changes; and the UI supports keyboard and assistive technology with understandable loading, empty, denied and conflict states. Attach Docker migration/API/UI outputs, browser/accessibility evidence and query-plan measurements. Record remaining Phase 1/2/3/4 gaps separately. Until this evidence exists, Phase 4 remains planned or in progress as appropriate; this blueprint itself does not establish completion.
