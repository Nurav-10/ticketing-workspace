# Auth-flow boundary

`AuthFlowService` coordinates verified OIDC claims, exact provider-identity resolution, invitation redemption or trusted bootstrap, and app-owned session issuance. Startup composes the OIDC provider, Prisma-backed services, session store, encrypted transaction store, and persistent rate limits when complete settings are supplied; otherwise it remains fail-closed. This integration has not yet been verified in Docker.

The public login routes accept no redirect target. Invitation login accepts the raw opaque invitation token only in a same-origin POST body, hashes its canonical ASCII representation, and passes only the digest into OIDC transaction context. Existing identities redeem that digest through the repository's atomic `{ userId, tokenHash }` seam, which rechecks persisted verified email, active user state, invitation state, and membership. New identities use the existing atomic `provisionFromInvitation` contract. A grant is never silently discarded and an identity never receives a session if the grant fails.

OIDC transaction context supports exactly one optional canonical base64url SHA-256 digest: `invitationTokenHash` or `bootstrapGrantHash`. The provider validates this shape; `PrismaLoginTransactionStore` encrypts it in the AES-GCM payload and validates it again after authenticated decryption. The context is returned only after the transaction is consumed and OIDC validation succeeds. Raw invitation tokens and bootstrap operator secrets are never persisted in the transaction or sent in redirect URLs.

Bootstrap remains an operator-controlled flow. `beginBootstrapLogin` derives the canonical digest with `deriveBootstrapGrantHash` and checks it in constant time before starting OIDC. Callback completion checks it again with the verified identity and creates the configured first workspace atomically.

`registerBootstrapRoutes` provides a transport adapter for an operator-facing first-workspace setup page. It is deliberately a separate router: the composition root must mount it only when bootstrap is explicitly configured and must supply a dedicated persistent rate limiter (per-client IP, with trusted proxy handling as configured). The operator secret is accepted only in an exact-origin `application/x-www-form-urlencoded` POST body, never in a URL; request parsing errors are converted to generic responses rather than forwarded to error loggers. The secret is passed directly to `beginBootstrapLogin`, then the local reference is discarded. The route sets the same short-lived `__Host-oidc_login_tx` Secure, HttpOnly, SameSite=Lax cookie used by the callback and redirects only to an HTTPS provider URL. The auth callback route must be mounted on the same Express app so it can consume that cookie and issue the app session.

Startup mounts the route at `/api/v1/auth/bootstrap` only when a high-entropy operator secret's digest and the trusted workspace name and slug are configured. It requires a dedicated persistent bootstrap limiter. Restrict network access where operations allow and remove bootstrap configuration after first use. Staging verification remains required before production activation.

The HTTP adapter sets transaction and app-session cookies as Secure, HttpOnly, SameSite=Lax, Path=/ cookies with `__Host-` names, clears transaction state after callback, uses only the fixed configured HTTPS public origin for redirects, and provides same-origin POST logout with server-side session revocation. Callback errors are generic and do not return codes or token material. Hosted login remains unavailable for a plain HTTP local origin; both issuer and callback remain HTTPS-only.
